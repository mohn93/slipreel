# GTM review fixes — 9 September 2026

The six findings in the final GTM review are implemented in source. The owner
confirmed that payment and activation worked; those are recorded as successful
owner acceptance checks, and no repeat purchase was made.

These changes require publication of a new macOS release and the updated website.
They do not change the already-published 1.0.14 binary by themselves.

## Repairs

| Finding | Change |
|---|---|
| F1 — privacy mismatch | Website privacy, Settings and onboarding now disclose account-associated usage/diagnostics and optional feedback email sent through PostHog. |
| F2 — cross-account attribution | Identity is attached at enqueue and persisted per event. Each launch/sign-out uses a fresh anonymous identity. Only a fresh anonymous session can join its first account; A is never treated as anonymous when switching to B. Queued diagnostics and feedback retain their owners across restarts. |
| F3 — failed autosave | A dirty-state controller retains the latest snapshot after failed writes. The editor shows Saved/Saving or Unsaved edits with Retry save. Route exit and native window close/Cmd+Q wait for pending saves and refuse exit when saving fails. Explicit recording deletion drains/cancels pending saves first. |
| F4 — premature feedback success | Feedback says sent only after acknowledgement; durable offline feedback is labeled saved on this Mac. Disk/network failure keeps the message visible for retry and provides an email fallback. Duplicate submits remain blocked. |
| F5 — unbounded queue/retry | Memory and disk queues are bounded to 500 events and approximately 1 MiB. Individual events are limited to 64 KiB; batches contain at most 100 events. Retries back off from five seconds to five minutes; disposal cannot restart timers. Disk writes are atomic, serialized and coalesced. |
| F6 — website wording | Homepage now says Check for updates in Settings, signing wording is corrected, and pricing refers to the current release instead of a withdrawn build. |

Legacy queued events without an identity are discarded during migration, rather
than assigned to whichever account is currently signed in. This affects only
pending telemetry/feedback. Recordings, project edits, license credentials and
preferences are unaffected. Already-sent events in PostHog are not rewritten or
deleted by the client repair.

Save failures preserve dirty snapshots for retry. As with other desktop apps,
force-killing the process or losing power before a successful save cannot be
made equivalent to an orderly saved exit. The native exit guard cancels an exit
request if the Dart save response stalls beyond fifteen seconds.

An off-host backup means a copy outside the server running Slipreel. A local
backup protects against some mistakes but can disappear with a failed or lost
server. Alerts need a destination where the owner will actually see a failure.

The owner has not selected an external storage/alert destination. No paid
service, new account, data upload, retention policy, or notification recipient
was invented or configured. The concrete remaining setup is: select a private
backup destination; store an encrypted copy there with a separately recoverable
key; restore that copy to an isolated database; configure readiness and
backup-failure alerts; verify receipt by the owner. Include signing/configuration
material and supported release artifacts in the recovery plan.

Historical PostHog retention/access review also remains an account-level step:
inspect the affected period and determine any cleanup from actual exposure
records. The app fixes prevent the reviewed future behavior; they do not prove
that older analytics history was removed.

The pre-existing Podfile.lock change and unrelated strategy/installer-withdrawal
files are preserved and excluded from the repair commit.
